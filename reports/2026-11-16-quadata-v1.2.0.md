# Pipeline quality: larplarpsahur 1.2.0 on Round 3 (quadata), scored against the Drive tables

Evaluation of `larplarpsahur-results.zip` from the 2026-11-16 QDC run of app 1.2.0
(OnSpeak47 `hymt2-125bit` @ `18f28fb2`). It is compared with the original Round 3
translation tables from the Google Drive dataset and with the 1.1.0 run
(`reports/2026-11-12-quadata-v1.1.0.md` on branch `claude/exciting-ramanujan-sw8xb0`).

The Drive tables are the three xlsx files bundled in the app under
`android/app/src/main/assets/reference_tables/`:

- `OneVoice_E_to_V_samples_100.xlsx` (sheet `Final`);
- `OneVoice_V_to_E_samples_100.xlsx` (sheet `Final`);
- `OneVoice_V_to_M_samples_180.xlsx` (sheet `Samples`).

## Summary

- **The references are right.** All 1,120 reference strings in the run (560 transcripts and
  560 translations) are byte-identical to the Drive tables. Every table ID was run and nothing
  is unmatched. The VE and VM references were read from the Hugging Face ZIP, so this also
  confirms the HF copy matches Drive, which had not been checked before.
- **The app's metrics are correct.** sacreBLEU 2.x reproduces the app's corpus BLEU and chrF
  to every printed digit for VE-vi, VM-vi and VM-zh. EV-en is 0.6 BLEU off, which is the known
  number-spelling difference for clock times.
- **The run is complete and clean:** 560 ok, 0 errors, 568 s wall-clock for 2,124 s of audio.
- **Vietnamese-source translation improved.** The kinship primer did what it was meant to.
  - **VE-vi (vi→en):** BLEU 31.8 → **33.8**, chrF 56.2 → **59.5**.
  - **VM-vi (vi→zh):** BLEU 33.7 → **35.4**, chrF 34.0 → **35.8**.
  - ***anh/chị* = "you":** now 1 he/she error in 21 sentences. The one error (VE-7938) also
    has an ASR slip. All three failures quoted in the 1.1.0 report are now translated as "you".
- **The 他 → 她 rule never fired.** No MT input contains 她. All 33 VM-zh sentences whose
  reference is about a woman still come out as *anh ấy*/*anh ta*. VM-zh scores are identical to
  1.1.0 to every digit. The rule needs a female word in the sentence, and none of these
  sentences has one.
- **EV-en (en→vi) dropped slightly**, from BLEU 30.1 / chrF 54.1 to **29.2 / 53.0**. The 1.2.0
  changes target Vietnamese and Chinese input, so this is unexplained. It is small for 100
  sentences, and without 1.1.0 per-sample outputs it cannot be tested.
- **ASR is unchanged.** As expected, all ASR metrics equal 1.1.0 exactly.
- **MT is slightly slower on Vietnamese input:** median +35–42 ms. Total MT time rose from
  319 s to 344 s.

## 4. The 1.2.0 changes, checked on the output

**Kinship primer (Vietnamese source).**

- **Pronouns:** in 21 VE sentences, the source uses *anh/chị* and the reference uses "you". 20
  are now translated with "you".
  - **Fixed examples:**
    - "Anh còn phiếu bảo hành không?" → "Do you still have a warranty ticket?";
    - "Cuối tuần này anh có rảnh không?" → "Do you have time this weekend?";
    - "Anh chờ tôi một chút." → "Please wait for me for a moment.";
    - "Anh đã sử dụng bao lâu?" → "How long has it been since you used it?".
  - **Remaining error:** VE-7938, "Anh rời phòng ngay và dùng cầu **thanh** bộ" → "**He**
    left the room right away and used the **escalator**". The transcript has an ASR slip
    (*thang* → *thanh*), and the output is still wrong.
- **Primer leakage:** no output contains a "Hello" / 你好 / *chào* that the input lacks.
- **Also fixed:** VE-2657 now keeps "tomorrow" and the future tense.

**他 → 她 rule (Chinese source).**

- 0 of 180 MT inputs contain 她.
- The reference is about a woman in 33 VM-zh sentences. All 33 outputs use a male pronoun.
  The 1.1.0 report counted 22 with a narrower criterion. The outputs did not change.
- Typical inputs are "他是哪国人？" and "我和他上周去河内酒店跳舞了。". None of them has a
  female word for the rule to key on, so the gender cannot be recovered from the transcript.
- The Vietnamese side shows that the MT itself handles gender. Where the source says *cô ta*,
  VM-vi correctly writes 她.
- An oracle run (`mt_mode=both`) would confirm this. A real fix needs speaker or discourse
  context, not a sentence-level rule.

**MT input shaping.** `mt_in` now records the exact text sent to the MT. It differs from the
transcript in 32 samples. The differences are capitalisation, the `writtenForm` digits
("sáu giờ ba mươi" → "6h30", 一百零一 → 101) and lowercased English in EV. None looks
harmful.

The run has none of the following:

- empty translations, apart from EV-2748, which has an empty transcript;
- output in the wrong language;
- copied rows;
- runaway repetition.

The rows with an extreme length ratio are explained by known causes:

- **Truncated references:** VM-5201, VM-0383, VM-1989, VM-5942.
- **ASR content mismatch,** where the audio should be checked by listening: VM-5919, VM-7149
  and VM-7215.
- **Format mismatch:** EV-6929, "gmt+430" against a spelled-out reference.

Many of the lowest-scoring VM-vi rows are valid paraphrases, for example "非常美味" against
"很好吃" (chrF 0) and "周日你会早起吗" against "星期天你起得早吗". Single-reference metrics
understate Chinese output.

  variance.

## 7. Recommendations

1. **Keep the primer.** It is the clearest quality gain since 1.1.0: +2 BLEU / +3 chrF on
   VE-vi and +1.7 BLEU on VM-vi, at about 40 ms of extra MT time.
2. **Don't count on the 她 rule for this dataset.** It never fires here. Either report
   VM-zh with gender-neutral scoring (the lenient profile already merges 她/他 on the ASR
   side), or measure the effect with an oracle run.
3. **Look into the EV-en drop** (−0.9 BLEU, all of it in sentences with a correct
   transcript). Keep `results.json` from every run, so the next comparison can diff outputs
   per sample and run a paired bootstrap test instead of comparing aggregates.
4. **Report the four truncated rows and the VM-4999 mismatch to the organisers.** These defects
   are in the official Drive tables, not just a copy.
5. **The open items from the 1.1.0 report are still open:**
   - an oracle run;
   - listening checks of VM-vi clips VM-1328, VM-3775 and VM-1506, and of VM-5919, VM-7149,
     VM-7215 and EV-2748;
   - a small human evaluation;
   - the "giờ" clock rule in `Numbers.java`.
